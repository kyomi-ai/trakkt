### Major Issue: `unwrap_or_default()` on schema serialization violates CODING_STANDARDS.md

**File:** `apps/server/src/routes/mcp.rs`, line 424

```rust
let schema_value = serde_json::to_value(&schema).unwrap_or_default();
```

`CODING_STANDARDS.md` is unambiguous: "Never use `unwrap_or_default()` on deserialization (JSON parse, filter decode, etc.) — use `match` and log the error with `tracing::warn!`." This code uses `unwrap_or_default()` on a `serde_json::to_value` call, which is a serialization operation that can fail. Silently falling back to `Value::Null` (the default) would return a tool entry with a null schema to MCP clients, which breaks tool introspection in a way that is invisible in logs and hard to diagnose.

In practice, `schemars::Schema` is backed by JSON-compatible types and the `to_value` call is very unlikely to fail. But the standard exists precisely to enforce observable failure paths — the cost of adding a `match` is zero and the observability gain is real.

Required fix:

```rust
for op in crate::api::all_operations() {
    let schema = (op.json_schema)();
    let schema_value = match serde_json::to_value(&schema) {
        Ok(v) => v,
        Err(e) => {
            tracing::warn!(tool = %op.name, error = %e, "failed to serialize tool schema");
            continue;
        }
    };
    tools.push(json!({
        "name": op.name,
        "description": op.description,
        "inputSchema": schema_value,
    }));
}
```

Using `continue` skips the malformed entry rather than inserting a null schema, which is a more correct degradation (a missing tool is less harmful than a tool with a broken schema).

### Critical Issue: `handle_tools_list` in `mcp.rs` emits duplicate tool entries for all 17 migrated operations

**File:** `apps/server/src/routes/mcp.rs`, lines 438–774

The `handle_tools_list` function builds the MCP `tools/list` response from two sources:
1. A loop over `crate::api::all_operations()` (lines 421–436) — now includes all 23 operations (6 issues + 17 new).
2. A hardcoded block (lines 438–774) that still manually pushes all 17 new tool entries.

Because Phase 5 migrated all 17 tools into `all_operations()`, every one of them is now emitted **twice** by `handle_tools_list`: once from the registry loop, and once from the leftover hand-written block. An MCP client receiving a `tools/list` response with duplicate tool names either renders them twice in its UI or treats the response as a protocol violation. This is a functional breakage of the MCP surface.

The hand-written `tool_*` functions in `mcp.rs`, the 17-entry scope static match table (lines 831–842), and the 17 `tool_*` match arms in `handle_tools_call` (lines 858–874) are also now dead code — `is_registry_tool` returns `true` for all 17 names so the `else` branch is never reached. These must all be removed to eliminate dead code and compiler warnings.

Required fix:

1. Remove the hand-written block from `handle_tools_list` (lines 438–774 of current `mcp.rs`), leaving only the registry loop.
2. Remove the 17 hand-written `tool_*` function bodies (tool_add_comment, tool_list_labels, tool_create_label, tool_list_statuses, tool_list_teams, tool_add_relation, tool_remove_relation, tool_list_issue_relations, tool_list_projects, tool_get_project, tool_create_project, tool_update_project, tool_delete_project, tool_list_milestones, tool_create_milestone, tool_update_milestone, tool_delete_milestone).
3. Remove the static scope match entries for these 17 tools (lines 831–840), since `registry_tool_scope` now handles them all.
4. Remove the 17 match arms in the `else` dispatch block (lines 858–874), leaving only the `_ => Unknown tool` fallback.

After cleanup, `handle_tools_list` should look like:

```rust
fn handle_tools_list(id: Option<Value>) -> JsonRpcResponse {
    let mut tools = Vec::new();

    for op in crate::api::all_operations() {
        let schema = (op.json_schema)();
        let schema_value = match serde_json::to_value(&schema) {
            Ok(v) => v,
            Err(e) => {
                tracing::warn!(tool = %op.name, error = %e, "failed to serialize tool schema");
                continue;
            }
        };
        tools.push(json!({
            "name": op.name,
            "description": op.description,
            "inputSchema": schema_value,
        }));
    }

    JsonRpcResponse::success(id, json!({ "tools": tools }))
}
```
