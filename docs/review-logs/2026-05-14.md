### Major Issue 1: `#[allow(dead_code)]` on test struct violates CODING_STANDARDS.md

**File:** `apps/server/src/api/mod.rs`, line 166

`CODING_STANDARDS.md` explicitly prohibits `#[allow(dead_code)]`. The attribute was added to silence a compiler warning on the test-only `TestUpdateParams` struct. Remove the attribute. If the warning fires, construct the struct in the test body to satisfy the compiler:
```rust
let _ = TestUpdateParams { id: "x".into(), title: None, priority: None };
```
This makes the fields read and eliminates the warning without a lint suppression.

---

### Major Issue 2: `resolve_issue_key_and_number` missing from `context.rs`

**File:** `apps/server/src/api/context.rs`

The Phase 1 plan (task 4) explicitly requires this function:
> `resolve_issue_key_and_number()` — issue identifier parsing (extracted from current MCP helpers)

The function exists in `mcp.rs` (lines 1120–1146) and is called by 5 of the 6 issue tool handlers. Without it in `context.rs`, Phase 2 handlers will either re-implement the same resolution logic (duplication) or introduce it without a review checkpoint.

The new implementation should take typed parameters (not `&serde_json::Value`) since Phase 2 handlers receive typed API param structs:
```rust
pub fn resolve_issue_key_and_number(
    issue_identifier: Option<&str>,
    team_key: Option<&str>,
    issue_number: Option<i64>,
) -> ApiResult<(String, i32)>
```
Add at least two tests: one for the `issue_identifier` path, one for the `team_key`+`issue_number` fallback path.
