(2) **Stuck-flag risk** — confirmed there is exactly one `notify_one()` call site in the whole codebase (`manager.rs:523`), and it's gated on `!catching_up`, so the kill signal structurally cannot fire on a connection that's mid-catch-up — a kill can only race the guard by acting on some *other* task ending first (send_task's socket write failing), and `recv_task.abort()` in that case still drops the guard correctly, because Tokio task-abort drops the task's Future in place, which runs Drop for every value live across the suspended `.await` — this is standard Rust drop semantics, not a Tokio-specific guarantee, and holds independent of *why* the task was aborted. Independently verified the "never catching up twice on one connection" claim by tracing execution rather than trusting the comment: `recv_task`'s `while let Some(Ok(msg)) = ws_receiver.next().await` loop `.await`s `handle_client_message` (which directly `.await`s into `handle_sync_bootstrap`/`delta`, no `tokio::spawn`) to completion before it can loop back and read a second client message, so a second guard on the same connection's flag cannot be created until the first one has already dropped — this is true by construction, not a race that happens to usually resolve favorably. Coordinator's framing ("state whether TRA-9923's ordering weakens the argument") — answer: yes in theory, negligibly in practice, and it's already tracked separately rather than newly introduced.
