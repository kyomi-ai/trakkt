# Code Review: TRA-127 Phase 1 — Eager Base Directory Creation for Local Attachment Storage

**Date**: 2026-05-23
**Reviewer**: Code Review Architect
**File reviewed**: `crates/trakkt-auth/src/attachment_storage.rs`

---

## Summary

A single-function change to `create_storage()` that eagerly creates the base attachment
directory at startup when the local storage backend is selected. The root cause was a
500 error in production containers where the storage directory did not exist and the
`store()` method's per-workspace `create_dir_all` succeeded for the subdirectory but the
base path itself was either absent or unwritable. The fix is minimal, correctly scoped,
and follows the established error-handling conventions in the codebase.

## Positive Observations

**Error handling is correct.** The `map_err` wraps the I/O failure into
`trakkt_core::Error::Internal` with a descriptive message that includes the path, matching
the same pattern used throughout the file (e.g., the `store()` and `retrieve()` methods).
The error is propagated with `?` and surfaces as a startup panic via the `.expect()` in
`main.rs` — exactly the right behavior for a misconfigured environment.

**No silent discard.** The result is not ignored or swallowed; failure aborts startup with
a clear message. This satisfies the coding standard: "Never silently discard errors."

**Synchronous `std::fs` is appropriate here.** `create_storage()` is a synchronous
function called from `main.rs` during initialization, before request handling begins. Using
`std::fs::create_dir_all` rather than `tokio::fs::create_dir_all` is correct — there is no
async context to block. The `tokio::fs` calls inside `LocalAttachmentStorage`'s trait
implementations are appropriate because those are invoked from within async handler tasks.

**No regression on workspace subdirectory creation.** The existing
`tokio::fs::create_dir_all(&dir)` call inside `store()` (line 55) still handles the
per-workspace subdirectory (`{base}/{workspace_id}`). The new startup call only ensures the
base path exists; the two `create_dir_all` calls cover complementary layers and do not
duplicate each other.

**No banned patterns introduced.** No `#[allow(...)]` attributes, no `unwrap_or_default`,
no `let _ =`, no hardcoded values, no duplicated helpers.

**Error message includes the path.** The format string
`"Failed to create attachment directory '{}': {e}"` with the path interpolated gives an
operator enough context to diagnose a permissions or mount issue without reading source
code — a meaningful improvement over the pre-existing generic message in `store()`.

---

## Recommended Next Steps

1. The existing error message in `store()` (line 56) — `"Failed to create attachment
   directory: {e}"` — does not include the directory path. Consider aligning it with the
   new startup message for consistency, though this is cosmetic and not blocking.

2. If Phase 2 of TRA-127 introduces additional storage backends that also use local
   paths, ensure those backends receive the same eager-creation treatment in
   `create_storage()`.
