### Major Issue 2 (was Major): Duplicate state-to-CSS mapping — RESOLVED

`pr_state_color(state: &str) -> &'static str` is present at line 2531:

```rust
fn pr_state_color(state: &str) -> &'static str {
    match state {
        "open"   => "text-success-foreground",
        "merged" => "text-purple-600",
        "closed" => "text-error-foreground",
        _        => "text-muted-foreground",
    }
}
```

It is called from exactly two sites in `render_pr_link`:

- Line 2552: `let icon_class = link.state.as_deref().map(pr_state_color).unwrap_or("text-muted-foreground");`
- Line 2567: `let badge_class = pr_state_color(state);` (inside `if let Some(ref state) = state_label`)

The single source of truth eliminates the divergence risk flagged in the initial review. The `draft` and unknown states both fall through to `text-muted-foreground` in both call sites, consistent with the original intent.

The `.unwrap_or("text-muted-foreground")` on line 2552 is applied to an `Option<&str>` → CSS class lookup, not to a serialization or deserialization operation. CODING_STANDARDS.md's prohibition on `unwrap_or_default()` targets serde operations specifically. This usage is correct.
